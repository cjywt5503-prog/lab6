# BioLIMS — лабораторна робота №6

## Що містить проєкт

Це окрема навчальна версія BioLIMS із лабораторної №5. Вона зберігає API Gateway, Keycloak, Consul, RabbitMQ, асинхронну обробку аналізу та SAGA. До сервісу замовлень додано координатор і два шарди. Кожний шард має основний вузол (primary), окрему SQLite-базу та асинхронну репліку з власною SQLite-базою.

Додано Prometheus, Grafana, Alertmanager, n8n та локальний журнал заявок про інциденти. Сервіси створюють JSON-логи, пов'язані через W3C `traceparent` і `trace_id`. Логування реалізує кореляцію в консолі Docker; Loki та Jaeger у цій конфігурації не встановлені, повноцінний експорт spans не реалізовано.

**Важливо:** це навчальна реалізація з фіксованими двома шардами і прикладною асинхронною реплікацією записів через HTTP. Це не вбудована реплікація PostgreSQL, не production-кластер і не система автоматичного перемикання на репліку. Показник `biolims_replication_lag_seconds` — вік найстарішого запису, який очікує підтвердження репліки; коли таких записів немає, він дорівнює нулю. Навчальний workflow створює заявки у власному локальному журналі; реальну інтеграцію з Jira або Slack у цьому проєкті не налаштовано. Автоматизація базується на правилах, а не на AI-моделі.

## 1. Підготовка

Потрібен Docker Desktop із Linux containers та інтернетом для першого завантаження образів. Розпакуйте папку `BioLIMS_Lab6`, наприклад у `D:\BioLIMS_Lab6`.

Лабораторна №5 використовує частину тих самих портів. Якщо вона працює, зупиніть її командою `docker compose stop` у папці **попередньої** лабораторної або через Docker Desktop. Її томи видаляти не потрібно. ЛР6 створює окремий Compose-проєкт і власні томи; старі записи до нього автоматично не переносяться.

У PowerShell відкрийте папку ЛР6 і виконайте:

```powershell
cd D:\BioLIMS_Lab6
docker compose up -d --build
docker compose ps
```

Перший запуск може тривати кілька хвилин через завантаження образів і запуск Keycloak. Дочекайтеся запуску контейнерів. Якщо з'явився `port is already allocated`, зупиніть програму або попередній проєкт, який займає цей порт. Логи компонента: `docker compose logs --tail=100 ІМ'Я_СЕРВІСУ`.

## 2. Налаштування n8n — обов'язковий крок

1. Відкрийте http://localhost:5678 та створіть локальний обліковий запис власника n8n. Його реєстрація потрібна лише в локальному n8n.
2. Створіть порожній workflow. У меню з трьома крапками оберіть **Import from File** та виберіть файл `monitoring\n8n\biolims_incidents.json` з розпакованої папки.
3. Збережіть workflow і переведіть його в стан **Active**. Саме активний workflow реєструє робочий `/webhook/biolims-alerts`.
4. Переконайтесь, що вузли з'єднані: `Alertmanager webhook` → `Підготувати інциденти` → `Створити або оновити інцидент`.

Alertmanager надсилає події на n8n у мережі Docker. n8n створює або оновлює окремі заявки в локальному журналі за `fingerprint` події. Повторення однієї події не створює нову заявку, а подія `resolved` змінює її стан на `resolved`. Подивитися заявки можна на http://localhost:8005 або JSON на http://localhost:8005/incidents. Перевіряйте також вкладку **Executions** в n8n: сам факт активації workflow ще не доводить доставку інциденту.

Якщо потрібна саме Jira або Slack, вузол створення інциденту треба замінити або доповнити відповідною інтеграцією n8n та додати власні облікові дані. Локальний журнал не слід називати Jira чи Slack у звіті.

## 3. Перевірка BioLIMS

Відкрийте http://localhost:8080, натисніть **Увійти** та використайте навчальний обліковий запис `student` / `Student123!`. Після входу виконайте **Отримати замовлення** та **Запустити аналіз** для `CODE128-1001`, а після завершення — **Отримати звіт**. Щоб перевірити інший шард, отримайте замовлення `CODE128-1002`. У відповіді координатора поле `shard` показує номер шарда. Це навчальні дані.

Для отримання замовлення необхідний scope `orders.read`, для запуску — `assays.run` та `orders.read`, для звіту — `reports.read`. Якщо Keycloak ще завантажується, зачекайте і повторіть. Вхід через GitHub із лабораторної №5 не перенесено автоматично: realm знову імпортується з файлу.

## 4. Метрики і дашборд

Відкрийте:

- Prometheus Targets: http://localhost:9090/targets — перевірте, що координатор, обидва основні шарди та обидві репліки мають стан `UP`.
- Grafana: http://localhost:3000 — навчальний логін `admin`, пароль `admin-lab6-demo`. Відкрийте папку **BioLIMS** → **BioLIMS — спостережуваність**.
- Alertmanager: http://localhost:9093 — активні сповіщення.

Дашборд містить доступність вузлів, p50/p95/p99 затримки, кількість запитів за секунду, частку відповідей 5xx, число замовлень на кожному основному шарді, відставання реплікації та ресурсні метрики процесів. Значення p50/p95/p99 оцінюються за гістограмами за останні дві хвилини. Без запитів деякі графіки спочатку будуть порожні.

Для створення трафіку:

```powershell
docker compose exec order-sample-service python lab6_scripts/demo_traffic.py
```

Зачекайте 30–60 секунд, оновіть дашборд. Це навчальні запити до внутрішнього тестового endpoint; для перевірки реального бізнес-сценарію також виконайте дії з розділу 3. `/metrics`, `/health`, `/lab6/demo` доступні всередині мережі Docker без JWT; останній endpoint призначений лише для локального навчального тесту.

## 5. Перевірка кореляції логів

Запустіть аналіз через сторінку BioLIMS і подивіться логи:

```powershell
docker compose logs --since 5m assay-execution-service order-sample-service shard-1-primary validation-report-service | Select-String 'trace_id'
```

Для одного запуску аналізу знайдіть однаковий `trace_id` у записах HTTP-запиту сервісу аналізу, координатора і відповідного шарда, а потім в `assay.event_received` сервісу звітів. Запуск `CODE128-1001` маршрутизується на шард 1. `span_id` відрізнятиметься між сервісами, а `parent_span_id` допомагає простежити їхній зв'язок. У звіт не вставляйте access token та інші секрети.

## 6. Перевірка сповіщень та n8n

Перш ніж почати, виконайте розділ 2 і впевніться, що n8n workflow активний.

### 6.1 Недоступний вузол і відставання реплікації

```powershell
docker compose stop shard-0-replica
docker compose exec shard-0-primary python lab6_scripts/create_replication_demo.py
```

Друга команда створить унікальне навчальне замовлення на основному шарді 0. Оскільки репліка вимкнена, черга реплікації почне накопичуватися. Після приблизно 30–90 секунд перевірте Grafana та http://localhost:9093: очікуються `BioLIMSNodeDown` і `BioLIMSReplicationLag`. Потім перевірте виконання workflow в n8n і журнал http://localhost:8005. Запишіть фактичний результат та зробіть скриншоти.

Обов'язково відновіть репліку:

```powershell
docker compose start shard-0-replica
```

Після повторної передачі запису значення черги й відставання мають повернутися до нуля. Переконайтеся, що відповідні події перейшли до `resolved` у журналі інцидентів; це може зайняти ще декілька десятків секунд.

### 6.2 Висока затримка p99

```powershell
docker compose exec order-sample-service python lab6_scripts/demo_traffic.py --slow
```

Скрипт окремо надсилає до координатора 12 запитів із затримкою 0,8 секунди. При p99 понад 0,5 секунди протягом 15 секунд має виникнути `BioLIMSHighLatencyP99`. Перевіряйте стан у Prometheus / Alertmanager та результат у n8n і журналі інцидентів. Після припинення навантаження значення зникне із двохвилинного вікна, а подія згодом має перейти в `resolved`.

## 7. Що зафіксувати для звіту

1. Контейнери `docker compose ps` і Prometheus Targets.
2. Приклади двох замовлень із номерами шардів та запуск аналізу.
3. Дашборд Grafana з метриками після створення трафіку.
4. Фрагмент JSON-логів із одним `trace_id` у кількох сервісах.
5. Недоступність репліки, графік затримки та активні правила в Alertmanager.
6. Активний workflow і його успішне виконання в n8n; заявка в локальному журналі та її стан після відновлення вузла.
7. Результат тесту високого p99, якщо спрацювання підтверджено.

Опис і місця для фактичних результатів наведені у файлі `REPORT_TEMPLATE.md`. Не стверджуйте, що перевірка пройдена, до отримання її фактичного результату.

## 8. Автоматизовані перевірки та завершення

За наявності Python і залежностей (`pip install -r requirements-test.txt`) можна виконати:

```powershell
python -m unittest discover -s tests -v
```

Тести перевіряють, зокрема, аутентифікацію, розподіл за шардами, реплікацію з SQLite, кореляцію W3C trace та створення заявок. Мережевий обмін між сервісами й RabbitMQ у тестах замінюється тестовими викликами: вони не замінюють перевірку повної системи в Docker.

Щоб зупинити проєкт і зберегти дані:

```powershell
docker compose down
```

Не додавайте `-v`, якщо потрібно зберегти дані ЛР6. Конфігурація локальна навчальна: мережеві порти відкриті лише на localhost, використовуються демо-паролі й HTTP. Без змін її не слід розгортати у відкритій мережі.
